1. PROJECT VISION & OBJECTIVE
----------------------------------------------------------------------

  Goal: Build an automated pipeline that converts ANY construction PDF
  (structural, architectural, multi-floor buildings) into a SketchUp
  3D model at LOD 300-400 fidelity, output as executable Ruby (.rb) script.

  Input:   PDF ban ve xay dung (structural plans, elevations, sections,
           schedules)
  Output:  SketchUp Ruby script -> load directly into SketchUp -> 3D model

  Target accuracy: > 70% visual similarity to source PDF
  Current accuracy: ~1% (critical gap identified, V6 plan in place)

----------------------------------------------------------------------
4. CRITICAL BUGS REMAINING (Root Causes of 1% Accuracy)
----------------------------------------------------------------------

  [CRITICAL] 1. GRID LABEL NOISE
     - X-axis: Numbers 21, 90, 0, 02, 61, 40 leak through filter
     - Y-axis: Only 2 labels detected (A, C) -- should be A,B,C,D,E,F,G
     - Impact: All column/beam positions are wrong -> model disconnected

  [CRITICAL] 2. MEMBER DETECTION = ZERO
     - 0 columns detected, 0 beams detected across all floors
     - Schedule extraction doesn't feed into element placement
     - Impact: Output is empty geometry / placeholders only

  [CRITICAL] 3. LEVEL MARKERS MISSING
     - Only ROOF, BASE, GROUND detected
     - No FL1-FL9 elevation markers extracted from elevation pages
     - Impact: Wrong Z-heights per floor

  [HIGH] 4. NO MULTI-PAGE CONSENSUS
     - Each page analyzed independently -- no cross-page data merging
     - Grid from page 1 might differ from page 2 -> inconsistent model
     - No spatial clustering or stability filter

  [HIGH] 5. PIPELINE PROLIFERATION
     - 7 pipeline variants exist (V1, V2, V3, V4, V5 + phase1 + pipeline_v5)
     - All half-baked, no single complete end-to-end path
     - Maintenance nightmare, bugs repeat across versions

5. ARCHITECTURE EVOLUTION
----------------------------------------------------------------------

  CURRENT (V4/V5 Architecture):

    PDF -> Phase 0: Classifier -> Phase 1: Scanner -> Phase 2: Extractor
        -> Phase 3: Coder (Ruby Generator) -> .rb file

  PROBLEMS WITH CURRENT ARCH:
    * LLM does all heavy lifting -> hallucination, inconsistency
    * No structured PDF parsing (pdfplumber unused effectively)
    * No cross-page data fusion
    * Single-pass extraction -> no verification loop


  TARGET (V6 Architecture -- Programmatic-First + LLM Verifier):

    PDF INPUT
        |
        v
    +----------------------------------------------+
    | PHASE 0: PDF STRUCTURED PARSER               |
    |  * pdfplumber: extract all text tokens        |
    |  * Extract vector lines per page             |
    |  * Output: RawPageData[]                     |
    +----------------------+-----------------------+
                           |
                           v
    +----------------------------------------------+
    | PHASE 1: PAGE CLASSIFIER (rule-based)        |
    |  * plan | elevation | section | schedule     |
    |  * Line density + text patterns              |
    |  * Output: ClassifiedPage[]                  |
    +----------------------+-----------------------+
                           |
             +-------------+----+--------+--------+
             v             v    v        v
    +---------+  +---------+ +-------+ +----------+
    |  PLAN   |  |  ELEV   | | SECT  | | SCHEDULE |
    |  EXTR   |  |  EXTR   | | EXTR  | | EXTRACT  |
    +----+----+  +----+----+ +---+---+ +----+-----+
         |            |          |          |
         +------------+----------+----------+
                      |
                      v
    +----------------------------------------------+
    | PHASE 2: CROSS-PAGE CONSENSUS ENGINE         |
    |  * Merge grid labels from ALL pages           |
    |  * Spatial clustering + stability             |
    |  * Dimension chain -> mm resolution           |
    |  * Level markers -> Z-height assignment       |
    |  * Output: UnifiedBuildingModel              |
    +----------------------+-----------------------+
                           |
                           v
    +----------------------------------------------+
    | PHASE 3: LLM VERIFIER (lightweight)           |
    |  * Send page image + extracted data           |
    |  * LLM only FILLS GAPS, not primary extract   |
    |  * Output: VerifiedBuildingModel             |
    +----------------------+-----------------------+
                           |
                           v
    +----------------------------------------------+
    | PHASE 4: RUBY GENERATOR (template-based)      |
    |  * LOD300: Columns + Beams + Slabs           |
    |  * LOD350: + Connections + Openings          |
    |  * LOD400: + Bolts + Welds + Details         |
    |  * Output: lod300_model.rb                   |
    +----------------------------------------------+

  KEY PRINCIPLES:
    * PROGRAMMATIC-FIRST: pdfplumber + math engine -> fast, cheap, deterministic
    * LLM AS VERIFIER: Gemini only to fill gaps, not primary extraction
    * CROSS-PAGE FUSION: Merge data from all pages for consistency
    * SINGLE PIPELINE: One code path, no more V1-V5 proliferation

----------------------------------------------------------------------
10. LESSONS LEARNED
----------------------------------------------------------------------

  1. LLM-FIRST EXTRACTION FAILS
     * Gemini hallucinates positions, invents members, misses obvious elements
     * Solution: Programmatic extraction first, LLM only for verification

  2. GRID IS THE FOUNDATION
     * Without accurate grid, ALL positions are wrong
     * Grid must be the FIRST thing perfected, not an afterthought

  3. CROSS-PAGE CONSENSUS IS ESSENTIAL
     * Construction PDFs spread data across multiple pages
     * Single-page analysis = incomplete/inconsistent data

  4. PIPELINE PROLIFERATION KILLS PROGRESS
     * 7 half-baked pipelines = zero working pipelines
     * Must consolidate to ONE clean code path

  5. SCHEDULE PAGES ARE GOLD
     * Member dimensions, materials, marks all in schedule tables
     * Currently underutilized -- schedule extraction must feed member placement

  6. PDFPLUMBER > IMAGE-ONLY
     * Text extraction from PDF vectors is deterministic and accurate
     * Image-based (Vision API) should be fallback, not primary
